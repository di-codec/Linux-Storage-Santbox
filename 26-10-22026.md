## Шаг 2: сеть Fabric A / Fabric B

**Зачем:**

- Через NAT ВМ друг друга не видят: VirtualBox даёт каждой ВМ свою изолированную NAT-сеть.
- Две отдельные сети дают client01 **два независимых пути** к storage01.
- NAS (шаг 3) будет работать через одну из них (Fabric A).
- SAN-multipath (шаг 6) использует обе, как Fabric A и Fabric B в продакшене.

**Fabric** - сеть хранения в FC SAN (набор FC-коммутаторов). В продакшене строят две независимые фабрики A и B: у сервера и массива по порту в каждой, фабрики между собой не соединены. При отказе одной фабрики multipath продолжает работу через вторую. Изменения делают на одной фабрике за раз.

### 2.1. VirtualBox: создать сети (один раз, обе ВМ выключены)

Host-only сеть - это виртуальный **коммутатор** VirtualBox на Windows. Он не принадлежит ни одной ВМ: создаётся один раз, потом обе ВМ подключаются к нему.

1. File → Tools → Network Manager → вкладка **Host-only Networks** → **Create**.
2. Первая сеть: вкладка Adapter → Configure Adapter Manually, IPv4 `192.168.56.1`, маска `255.255.255.0`. Вкладка DHCP Server: **Enable Server выключить** → Apply.
3. Снова **Create**, вторая сеть: `192.168.57.1`, маска `255.255.255.0`, DHCP выключен → Apply.

`192.168.56.1` и `192.168.57.1` - адреса самой Windows в этих сетях. **Адреса у всех машин разные**, одинаковые только маски и подсети:


| Кто            | Fabric A            | Fabric B            |
| -------------- | ------------------- | ------------------- |
| Windows (хост) | 192.168.56.1        | 192.168.57.1        |
| storage01      | 192.168.56.10       | 192.168.57.10       |
| client01       | 192.168.56.20       | 192.168.57.20       |
| Маска          | 255.255.255.0 (/24) | 255.255.255.0 (/24) |


**DHCP не нужен:** в storage-сетях адреса статические, адрес хранилища не должен меняться.

### 2.2. VirtualBox: адаптеры каждой ВМ (ВМ в состоянии Powered Off, не Saved)

Settings → Network:

- **Adapter 1**: NAT, не трогать (интернет + SSH на 2222 для storage01 / 2223 для client01).
- **Adapter 2**: Enable → Attached to: Host-only Adapter → сеть с `192.168.56.1`.
- **Adapter 3**: Enable → Host-only Adapter → сеть с `192.168.57.1`.
- Advanced → **Cable Connected** включено (понадобится в шаге 6 для имитации "path down").

Сделать на **storage01** и на **client01** - обе ВМ подключаются к одним и тем же двум коммутаторам.

### 2.3. storage01: после загрузки

⚠️ Перезагрузка отключает loop-устройства, поэтому сначала восстанови хранилище:

```
sudo bash remount-storage01.sh
```

Найди имена новых интерфейсов:

```
ip -br link
```

```bash
[p@storage01 ~]$ ip -br link
lo               UNKNOWN        00:00:00:00:00:00 <LOOPBACK,UP,LOWER_UP>
enp0s3           UP             08:00:27:0e:07:c1 <BROADCAST,MULTICAST,UP,LOWER_UP>
enp0s8           UP             08:00:27:eb:72:77 <BROADCAST,MULTICAST,UP,LOWER_UP>
enp0s9           UP             08:00:27:0f:c4:26 <BROADCAST,MULTICAST,UP,LOWER_UP>
```

`enp0s3` = Adapter 1 (NAT), `enp0s8` = Adapter 2, `enp0s9` = Adapter 3. Имя = место карты на виртуальной шине PCI (`en` Ethernet, `p0` шина 0, `s8` слот 8).

Проверь, не создал ли NetworkManager автоматические DHCP-подключения на новых картах:

```
nmcli -f NAME,UUID,DEVICE con show
```

Если на `enp0s8`/`enp0s9` есть `Wired connection 1`/`2` - удали их (кавычки обязательны, в имени пробелы). `enp0s3` и `lo` не трогать:

```
sudo nmcli con delete "Wired connection 1"
sudo nmcli con delete "Wired connection 2"
```

Создай подключения:

```
sudo nmcli con add type ethernet ifname enp0s8 con-name fabricA ipv4.method manual ipv4.addresses 192.168.56.10/24
sudo nmcli con add type ethernet ifname enp0s9 con-name fabricB ipv4.method manual ipv4.addresses 192.168.57.10/24
sudo nmcli con up fabricA && sudo nmcli con up fabricB
```

- `con add type ethernet` - создать постоянное подключение (файл в `/etc/NetworkManager/system-connections/`), переживёт reboot.
- `ifname` - к какому интерфейсу оно привязано.
- `con-name` - понятное имя подключения.
- `ipv4.method manual` - статический адрес, без DHCP.
- `ipv4.addresses 192.168.56.10/24` - адрес и маска (`/24` = `255.255.255.0`).
- Шлюз не указан намеренно: storage-сеть изолированная, интернет остаётся через NAT. С шлюзом Linux мог бы отправлять интернет-трафик в storage-сеть.
- `con up` - включить подключение сейчас. `&&` - вторая команда выполняется, только если первая успешна.



### 2.4. client01

Те же действия (проверка и удаление `Wired connection ...`, создание и включение `fabricA`/`fabricB`), только адреса `192.168.56.20/24` и `192.168.57.20/24`. Remount на client01 не нужен - хранилища там нет.

```bash
[p@client01 ~]$ ip -br link
lo               UNKNOWN        00:00:00:00:00:00 <LOOPBACK,UP,LOWER_UP>
enp0s3           UP             08:00:27:0e:07:c1 <BROADCAST,MULTICAST,UP,LOWER_UP>
enp0s8           UP             08:00:27:79:cc:96 <BROADCAST,MULTICAST,UP,LOWER_UP>
enp0s9           UP             08:00:27:d1:37:fa <BROADCAST,MULTICAST,UP,LOWER_UP>
```

> [!NOTE]
> MAC у `enp0s3` (NAT) на client01 совпадает с storage01 (`08:00:27:0e:07:c1`): при клонировании MAC первого адаптера не перегенерировался. Для NAT это безопасно - у каждой ВМ своя изолированная NAT-сеть. В общей сети одинаковые MAC вызвали бы конфликт. У `enp0s8`/`enp0s9` MAC разные - так и должно быть.



### 2.5. Проверка вручную

На обеих ВМ:

```
ip -br addr
```

Ожидаем:

- storage01: `enp0s8 UP 192.168.56.10/24`, `enp0s9 UP 192.168.57.10/24`
- client01: `enp0s8 UP 192.168.56.20/24`, `enp0s9 UP 192.168.57.20/24`

С client01:

```
ping -c 3 192.168.56.10   # путь через Fabric A
ping -c 3 192.168.57.10   # путь через Fabric B
```

`-c 3` - ровно 3 запроса. Оба ping должны пройти с `0% packet loss`.

### 2.6. Проверка скриптами

Скрипты только читают систему и ничего не меняют. Каждый запускается на своей ВМ.


| Скрипт                                                       | Где       | Запуск                                                                     |
| ------------------------------------------------------------ | --------- | -------------------------------------------------------------------------- |
| [check-step2-storage01.sh](scripts/check-step2-storage01.sh) | storage01 | `sudo bash ~/check-step2-storage01.sh` (sudo нужен для проверки firewalld) |
| [check-step2-client01.sh](scripts/check-step2-client01.sh)   | client01  | `bash ~/check-step2-client01.sh`                                           |


Что проверяется для каждой фабрики:

- интерфейс существует и UP;
- подключение `fabricA`/`fabricB` существует и активно на нужном интерфейсе;
- адрес статический (`manual`), ровно один и правильный (нет остатков DHCP вроде `.102`);
- на интерфейсе нет лишних подключений (`Wired connection ...`);
- ping до другой ВМ **через этот интерфейс** (`ping -I`) - каждая фабрика проверяется отдельно;
- один маршрут по умолчанию, через `enp0s3` (NAT);
- (только storage01) firewalld не блокирует ping.

Итог: **storage01 - PASS=17 FAIL=0, client01 - PASS=16 FAIL=0.**

> [!IMPORTANT]
> Без `sudo` скрипт storage01 выдаёт `Not Authorized ... run the application as superuser` в блоке firewall, и PASS по firewall в этом случае недостоверен.



## Troubleshooting шага 2 (что пошло не так и как исправлено)



### Симптом

```bash
[p@client01 ~]$ ping -c 3 192.168.57.10
PING 192.168.57.10 (192.168.57.10) 56(84) bytes of data.

--- 192.168.57.10 ping statistics ---
3 packets transmitted, 0 received, 100% packet loss, time 2018ms

[p@client01 ~]$ ping -c 3 192.168.56.10
PING 192.168.56.10 (192.168.56.10) 56(84) bytes of data.
From 192.168.56.102 icmp_seq=1 Destination Host Unreachable
From 192.168.56.102 icmp_seq=2 Destination Host Unreachable
From 192.168.56.102 icmp_seq=3 Destination Host Unreachable

--- 192.168.56.10 ping statistics ---
3 packets transmitted, 0 received, +3 errors, 100% packet loss, time 2009ms
pipe 3
```



### Причины (было три)

1. **DHCP на Host-only сетях VirtualBox не был выключен.** Он выдал client01 адрес `.102` (сервер DHCP VirtualBox сидит на `.100` и раздаёт с `.101`).
2. **На client01 работали автоматические подключения** `Wired connection 1`**/**`2` с DHCP, а не `fabricA`/`fabricB`.
3. **На storage01** `fabricA`**/**`fabricB` **не были созданы** - у `enp0s8`/`enp0s9` не было адресов вообще. Отвечать на ping было некому. Это выявил скрипт `check-step2-storage01.sh` (`connection fabricA does not exist`, `addresses: 'none'`).

**Как читать ошибки ping:**

- `Destination Host Unreachable` - клиент спросил в сети "у кого адрес `.10`?" (ARP-запрос) и не получил ответа: адреса `.10` в этой сети нет.
- Тихие `100% packet loss` без ошибок - у клиента нет адреса в этой подсети, пакет ушёл через маршрут по умолчанию (NAT) и потерялся.

- `enp0s8` получил `192.168.56.102` от DHCP VirtualBox вместо статического `.20`.

### Исправление

**1. VirtualBox: выключить DHCP** (ВМ можно не выключать)

File → Tools → Network Manager → Host-only Networks → для **каждой** из двух сетей:

- вкладка DHCP Server → снять галочку Enable Server → Apply;
- вкладка Adapter → адреса `192.168.56.1` / `192.168.57.1`, маска `255.255.255.0`.

Выключение DHCP **не отбирает** уже выданный адрес - его убирает только удаление `Wired connection ...`.

**2. client01: удалить автоматические подключения** (только на `enp0s8`/`enp0s9`)

```bash

sudo nmcli con delete "Wired connection 2"
```

**3. client01: создать и включить** `fabricA`**/**`fabricB` (если их нет)

```bash

sudo nmcli con add type ethernet ifname enp0s9 con-name fabricB ipv4.method manual ipv4.addresses 192.168.57.20/24
sudo nmcli con up fabricA && sudo nmcli con up fabricB
```

Ожидаем: на `enp0s8` только `192.168.56.20/24`, на `enp0s9` только `192.168.57.20/24`, никаких `.102`.

**4. storage01: создать и включить** `fabricA`**/**`fabricB`

### 3.1. storage01: открыть export для подсети
> [!IMPORTANT]
> Что такое подсеть в export. Запись `192.168.56.0/24` означает "все адреса от `192.168.56.1` до `192.168.56.254`".
* `/24` - сколько первых бит адреса составляюь номер сети 24 бита, то есть первые три числа.
* Так одним правилом разрешаешь доступ всем машинам Fabric A, а не прописываешь каждый IP.
* Можно и точнее: `192.168.56.20` (только client01) или `/32` (ровно один адрес).

#### 1. Проверить, что смонтирован том с данными, а не пустая папка
```bash
df -h /srv/nfs/share
```
В колонке Filesystem должно быть `/dev/mapper/labvg-labvol`. Если нет, сначала выполни `sudo bash remount-storage01.sh`.

#### 2. Текущее правило
```bash
cat /etc/exports
```
Ожидаем: `/srv/nfs/share 127.0.0.1(rw,sync,no_subtree_check,root_squash)`. Формат строки: `ПАПКА КЛИЕНТ(ОПЦИИ)`.

#### 3. Заменить клиента на подсеть
```bash
sudo sed -i 's|127.0.0.1(|192.168.56.0/24(|' /etc/exports
```

- `sed -i` - заменить текст прямо в файле.
- `s|ЧТО|НА ЧТО|` - команда замены. Разделитель `|`, потому что в `/24` есть слэш.
- Скобка `(` в шаблоне гарантирует, что заменится только клиент перед опциями.

#### 4. Применить и проверить
```bash
cat /etc/exports
sudo exportfs -ra
sudo exportfs -v
```

- `cat` должен показать `192.168.56.0/24(...)`.
- `exportfs -ra` перечитывает файл и применяет правила к работающему NFS-серверу.
- `exportfs -v` показывает, что сервер реально отдаёт сейчас. Опций там будет больше: добавятся значения по умолчанию (`wdelay`, `sec=sys`, ...).

> [!IMPORTANT]
> Firewall не трогаем: проверка уже показала, что nfs, mountd и rpc-bind открыты, а enp0s8 в зоне public.

### 3.2. client01: подключить шару

#### 1. Спросить у сервера, что он отдаёт
```bash
showmount -e 192.168.56.10
```
* `showmount -e` (exports) запрашивает список экспортов у службы `mountd` на storage01.
* Ожидаем:
```bash
  Export list for 192.168.56.10:
  /srv/nfs/share 192.168.56.0/24
```
* `mountd` - механизм NFSv3. Если команда зависает или ругается, проблема в сети, firewall или службах на сервере. С этой команды начинается troubleshooting NAS.

#### 2. Создать точку монтирования
```bash
sudo mkdir -p /mnt/share
```
Точка монтирования - пустая папка, к которой "приклеится" удалённая шара. `-p` - не ругаться, если папка уже есть.

#### 3. Смонтировать
```bash
sudo mount -t nfs 192.168.56.10:/srv/nfs/share /mnt/share
```
* `-t nfs` - тип: сетевая файловая система NFS.
* `192.168.56.10:/srv/nfs/share` - формат сервер:путь_на_сервере.
* `/mnt/share` - куда подключить на client01.

Монтирование временное, после перезагрузки client01 пропадёт. Постоянное через `/etc/fstab` сделаем позже.

#### 4. Проверить
```bash
df -hT /mnt/share
```
* `-T` добавляет колонку с типом файловой системы.
* Ожидаем тип `nfs4`, источник `192.168.56.10:/srv/nfs/share`, размер 6.0G и занято 183M - те же цифры, что на storage01.
```bash
ls -la /mnt/share | head
```
Ты должна увидеть свои состаренные данные, хотя физически их на client01 нет. `head` показывает первые 10 строк, чтобы вывод не был огромным.
```bash
nfsstat -m
```
* Показывает параметры каждого NFS-монтирования.
* Обрати внимание на `vers=4.2`: клиент и сервер сами договорились о самой новой общей версии.
* Ещё на `sec=sys` и `hard`. `hard` значит: если сервер пропадёт, клиент будет ждать и повторять запросы бесконечно, а не вернёт ошибку программе. Так безопаснее для данных.

### 3.3. client01, затем storage01: `root_squash` и UID
`root_squash` - защита: root на клиенте не считается root на сервере. Сервер подменяет его на `nobody` (UID 65534), у которого нет особых прав. Иначе любой, кто получил root на любой машине в сети `192.168.56.0/24`, получил бы полный доступ к данным.

#### client01
##### 1. Создать файл от root
```bash
sudo touch /mnt/share/root-test.txt
ls -l /mnt/share/root-test.txt
```
* `touch` создаёт пустой файл.
* Ожидаем владельца `nobody nobody`, а не `root root`.
* Root смог создать файл только потому, что на папке права `rwxrwxrwt`, а `nobody` входит в "все остальные".

##### 2. Создать файл от обычного пользователя
```bash
touch /mnt/share/p-test.txt
ls -ln /mnt/share/p-test.txt /mnt/share/root-test.txt
```
* `-n` показывает владельца числами (UID/GID), а не именами.
* Ожидаем: `p-test.txt` → `1000 1000`, `root-test.txt` → `65534 65534`.
##### 3. Root пытается удалить чужой файл
```bash
sudo rm /mnt/share/p-test.txt
```
* Ожидаем: `Permission denied`.
* Локально root может удалить что угодно. Здесь он превратился в `nobody`, а sticky bit разрешает удаление только владельцу (`p`). Это главная демонстрация: root клиента на сервере бессилен.

##### 4. Владелец удаляет свой файл
```bash
rm /mnt/share/p-test.txt
```
Проходит: `p` - владелец.

#### storage01
 
##### 5. Посмотреть файл root'а на сервере
```bash
ls -ln /srv/nfs/share/root-test.txt
```
* На сервере владелец тоже `65534`: подмена происходит на сервере при записи, а не только в отображении у клиента.

##### 6. Удалить тестовый файл
```bash
sudo rm /srv/nfs/share/root-test.txt
```
Здесь сработает: это локальный root storage01, на него `root_squash` не действует.

Почему UID важен (вопрос для интервью). NFS с `sec=sys` передаёт серверу не имя пользователя, а номер. У `p` UID 1000 на обеих машинах (client01 - клон), поэтому сервер считает его одним и тем же пользователем. Если бы на client01 у какой-нибудь `anna` тоже был UID 1000, она получила бы доступ к файлам `p`. В продакшене одинаковые UID на всех машинах обеспечивает LDAP или Active Directory. А несовпадение UID - классическая причина жалоб "вижу чужие файлы" и “permission denied на своих файлах”.

### 3.4 Сломать доступ (чужая подсеть) → access denied → починить
> [!IMPORTANT]
> Цель: увидеть ошибку, которую встретишь в реальной работе, и научиться находить её причину на сервере. Это сценарий troubleshooting №3 из плана (“NFS mount fails with access denied”).

#### client01: отключить шару
```bash
sudo umount /mnt/share
findmnt /mnt/share
```
`findmnt` ничего не выводит - шара отключена. Если выведет строку, повтори `umount`: шара была смонтирована дважды.

#### storage01: разрешить доступ только чужой подсети
```bash
sudo sed -i 's|192.168.56.0/24(|192.168.99.0/24(|' /etc/exports
sudo exportfs -ra
sudo exportfs -v
```
`192.168.99.0/24` - сеть, в которой нет ни одной нашей машины. Это имитирует ошибку администратора: опечатку в подсети или неправильный `clientmatch`.

#### client01: попытка подключиться
```bash
showmount -e 192.168.56.10
sudo mount -t nfs 192.168.56.10:/srv/nfs/share /mnt/share
```
* `showmount` по-прежнему ответит, но покажет `/srv/nfs/share 192.168.99.0/24`. Это первая подсказка: экспорт есть, но не для нас.
* `mount` выдаст `mount.nfs: access denied by server while mounting 192.168.56.10:/srv/nfs/share`.
* Важно: сеть и сервер работают (сервер ответил), отказ пришёл именно от правила доступа.

#### storage01: найти причину в логах
```bash
sudo journalctl --since "10 min ago" | grep -i mount
```
* `journalctl` - журнал systemd, где собираются логи всех служб.
* `--since "10 min ago"` - только записи за последние 10 минут.
* `grep -i mount` - только строки со словом “mount”, без учёта регистра.
* Ожидаем строку вроде `refused mount request from 192.168.56.20 for /srv/nfs/share (/srv/nfs/share): unmatched host`.
* `unmatched host` - адрес клиента не подходит ни под одно правило. Это точная причина.
#### storage01: починить
```bash
sudo sed -i 's|192.168.99.0/24(|192.168.56.0/24(|' /etc/exports
sudo exportfs -ra
sudo exportfs -v
```
#### client01: проверить
```bash
sudo mount -t nfs 192.168.56.10:/srv/nfs/share /mnt/share
df -hT /mnt/share
```
Снова `nfs4` и твои данные.

Порядок диагностики `access denied` (ответ на интервью):

1. Отвечает ли сервер вообще: `showmount -e`, `ping`.
2. Есть ли адрес клиента в правиле export: `showmount -e` на клиенте, `exportfs -v` на сервере.
3. Что пишет сервер: логи `mountd` - `unmatched host`, неверный путь.
4. Firewall и версия NFS.
