## Шапка: sheband & `set`
`set -euo pipefail` — **это страховочный пояс**. Разберём по флагам, потому что каждый ловит свой класс ошибок:

* `set -e` — скрипт падает на первой же команде, вернувшей ненулевой код. Без него скрипт при ошибке `pvcreate` спокойно поехал бы дальше делать `vgcreate` на несуществующем PV и оставил бы систему в поломанном полусобранном состоянии.
* `set -u` — обращение к необъявленной переменной становится ошибкой. Ловит опечатки: написал `${VG_NAM}` вместо `${VG_NAME}` — вместо тихой подстановки пустоты получишь явную ошибку. Без `-u` команда `vgcreate "" ...` могла бы натворить дел.
* `set -o pipefail` — в конвейере `a | b` по умолчанию код возврата берётся только от последней команды `b`. Если `a` упала, а `b` отработала — bash считает, что всё хорошо. `pipefail` заставляет всю строку считаться проваленной, если упало любое звено.

## 0: Parameters 
```bash
IMG_DIR="/var/lib/sandbox-disks"
DISK_COUNT=3
DISK_SIZE="2G"
```
Это просто переменные, вынесенные в одно место наверх, чтобы не искать «магические числа» по всему коду. Хорошая практика: меняешь конфигурацию в одном блоке, а не редактируешь тело скрипта.

**Альтернативы:** можно принимать эти значения как аргументы командной строки через `getopts` (`./sandbox-setup.sh -n 3 -s 2G`), или читать из внешнего конфиг-файла (`source config.env`). Для лаборатории вариант «правь наверху» самый простой и наглядный.

Обрати внимание на `EXPORT_OPTS` — это опции NFS-экспорта, к ним вернёмся в блоке 5.

### `log` **Function**
```bash
log() { printf '\n\033[1;32m==> %s\033[0m\n' "$*"; }
```
Просто печатает свой аргумент жирным зелёным с префиксом `==>`. `\033[1;32m` — это ANSI escape-код (`1` = жирный, `32` = зелёный), `\033[0m` — сброс форматирования обратно к обычному. Без сброса весь последующий вывод терминала остался бы зелёным.

**Почему** `printf`, **а не** `echo`. `printf` предсказуемо обрабатывает escape-последовательности и форматную строку на всех системах; `echo -e` ведёт себя по-разному в разных оболочках. Это стандартная рекомендация для переносимых скриптов.

Если запустить отдельно `log "Hello"`, увидишь:
```bash
==> Hello
```

## 1: packages & checks

```bash
if [[ "${EUID}" -ne 0 ]]; then
    echo "Run with sudo:  sudo $0" >&2
    exit 1
fi
```
`EUID` — effective user ID, встроенная переменная bash. У root он равен `0`. Операции с блочными устройствами, LVM и NFS требуют root, поэтому скрипт сразу отсекает запуск от обычного пользователя. `>&2` направляет сообщение в поток ошибок (stderr), а не в обычный вывод — правильно для сообщений об ошибках, чтобы их можно было отделить при перенаправлении.

**Альтернативы проверки root:** `[[ "$(id -u)" -ne 0 ]]` — то же самое, но через внешнюю команду `id` (работает и в оболочках без `EUID`). Хуже — `[[ "$(whoami)" != "root" ]]`, потому что завязка на имя, а не на UID (root мог быть переименован, хоть это и редкость).

```bash
dnf install -y nfs-utils lvm2
```
`dnf` — пакетный менеджер Fedora / RHEL / Rocky / AlmaLinux. `-y` автоматически отвечает «да» на все вопросы (иначе установка ждала бы подтверждения и скрипт завис бы). `nfs-utils` даёт сервер NFS и `exportfs`, `lvm2` — команды `pvcreate/vgcreate/lvcreate`.

Альтернативы под другие дистрибутивы (важно, если ьудем переносить скрипт):

* Debian/Ubuntu: `apt install -y nfs-kernel-server lvm2` — заметь, пакет NFS-сервера называется иначе.
* Старые CentOS 7: `yum install -y ...`.
* SUSE: `zypper install -y nfs-kernel-server lvm2`.

**❗ Именно из-за таких различий «универсальный» storage-скрипт обычно начинается с определения дистрибутива.**

## 2: Loop images
```bash
for i in $(seq 1 "${DISK_COUNT}"); do
    img="${IMG_DIR}/disk${i}.img"
    truncate -s "${DISK_SIZE}" "${img}"
    dev="$(losetup --find --show "${img}")"
    LOOP_DEVICES+=("${dev}")
done
```
Это ключевой трюк лаборатории: **сделать вид, что у нас есть настоящие диски, не имея их.**

`truncate -s 2G disk1.img` создаёт разреженный (sparse) файл. Он числится размером 2 ГБ, но на диске реально занимает почти ноль, пока в него ничего не записано. Место выделяется по мере записи.

Если проверишь отдельно:

```bash
$ truncate -s 2G disk1.img
$ ls -lh disk1.img       # «логический» размер
-rw-r--r-- 1 root root 2.0G ... disk1.img
$ du -h disk1.img        # реально занятое место
0       disk1.img
```
Вот это расхождение между `ls` (2 ГБ) и `du` (0) — характерная примета sparse-файла, и именно поэтому скрипт в конце советует потренироваться с `df`/`du`.

**Альтернативы созданию образа:**

* `dd if=/dev/zero of=disk1.img bs=1M count=2048` — старый способ, но он реально записывает 2 ГБ нулей, то есть занимает место сразу и работает медленнее.
* `fallocate -l 2G disk1.img` — быстро резервирует место, но файл не разреженный (место занято сразу). Быстрее, чем `dd`, но «честно» отъедает диск.

Для sandbox `truncate` идеален: три «диска» по 2 ГБ почти ничего не стоят, пока пустые.

`losetup --find --show disk1.img` привязывает файл к loop-устройству. `--find` берёт первый свободный `/dev/loopN`, `--show` печатает его имя, которое тут же захватывается в `dev`. После этого система видит `/dev/loop0` как обычный блочный диск.

Отдельный запуск:
```bash
$ losetup --find --show disk1.img
/dev/loop0
$ lsblk /dev/loop0
NAME   SIZE TYPE
loop0    2G loop
```
`LOOP_DEVICES+=("${dev}")` — накапливает имена в массиве, чтобы потом одним махом скормить их LVM. Массив (а не строку) используют, чтобы корректно передать несколько аргументов с сохранением границ (важно, если бы в путях были пробелы).

## 3: LVM (PV->VG->LV)

Секция о том-как из набора дисков делают один растяжимый том.

**Ⅰ. PV (physical volume)** ***физический том*** - это твой реальный диск или раздел, который ты отдаешь под управление **LVM.** Например целый cd//dev//sdb. 
**Ⅱ. VG (volume group)** *** группа томов*** - ты берешь один или несколько физических томов и сливаешь их в один большой котел. Скажем, 2 диска по 500 Гб, дают группу на терабайт. Система видит это как единое пространство.
**Ⅲ. LV (logical volume)** ***логический том*** - из общего котла ты нарезаешь куски нужного размера, и вот на них уже создаешь файловую систему и хранить данные. Один котел можно порезать на сколько угодно томов.

<img width="1224" height="1285" alt="linux-sandbox-LVM" src="https://github.com/user-attachments/assets/b7f480b1-8d64-4dcd-9dab-e55613e0ceb7" />


> [!NOTE] 
> **LVM = Logical Volume Manager**    
>📎 Менеджер логических томов в Linux. Добавляем слой между физическими дисками и файловыми системами.   
>  **3 уровня рвботы:** 
>   1. Физические тома - сами диски или разделы 
>   2. они собираються в группу томов, 
>   3. из неё нарезаются логические тома, на которых уже живут файловые системы        
>  ➕ **Гибкость:** логический том можно расширить на лету, растянуть на несколько дисков, или сделать мнгновенный снимок состояния. 

## 4: Filesystem + `mount` (файловые системы & мантирование)

> [!TIP]
> **LVM** дает блочное устройство `dev/labvg/labvol`, но это еще **"голый" том без файловой системы** - в него нельзя просто записать файл, <ins>*там нет структуры катологов, inode, ничего*</ins> **Блок 4** закрывает ровно этот разрыв: он берет блочное устройство от блова 3 и превращает его в мепсто куда можно класть файл.

### 3 строки делают три вещи:
- **mkfs.xfs** -> создает файловую систему (структура для зранения файлов) поверх тома.
- **mount** -> подключает эту файловую систему в точку `/srv/nfs/shares`, чтобы она стала обычной папкой в дереве каталогов
- **chmod 777** -> выставление прав пользования

## 5: NFS server

### Ⅰ `systemctl enable --now nfs server`

```bash
log "Configuring the NFS export"
systemctl enable --now nfs-server
```

`systemctlk` - управление сервирами через **systemd** (система инициализации и менеджер служб в современных *Linux:* отвечает за запуск, остановку и автозапуск [daemon](# "это фоновый процесс в Linux/Unix, который постоянно работает и обслуживает запросы, не привязанный к терминалу пользователя") ).

#### 📎Здесь 1 команда делает 2 действия сразу:
1. **enable ->** прописывает сервис `nfs-server` в автозапуск. Технически создает символическую ссылку, чтобы при следующей загрузке `systemd` поднял этот [daemon](# "это фоновый процесс в Linux/Unix, который постоянно работает и обслуживает запросы, не привязанный к терминалу пользователя") автоматическм. Без `enable` скрвис не переживет перезагрузку после reboot, расширенная папка `srv/nfs/share` просто перестает передоваться по сети клиентам.
2.  **--now ->** запускает сервер <ins>**прямо сейчас**</ins>, не дожидаясь перезагрузки. Это эквивалент отдельной команды `systemctl start nfs-server`.

### Ⅱ Разбор логической связки c `grep`

```bash
if ! grep -qF "${MOUNT_POINT}" /etc/exports 2>/dev/null; then
    echo "${EXPORT_LINE}" >> /etc/exports
fi
```
**Логическая цепочка:** добавь строку экспорта в `etc/exports`, но только если ее там еще нет. Следовательно, это защита от дублей при авторном запуске скрипта (идеопотентность - свойство при котором повторный запуск не портит уже сделаное). 
**❌ Разбор по частям:** 
* `grep -qF "${MOUNT_POINT}" /etc/exports` -> ищет строку  `srv/nfs/share` в файле `etc/exports` 
    * **-q = quite** - ничего не петатать, важен только ***код возврата*** (0 - нашлось, 0! - не нашлось) 
    * **-F = fixed string** - искать буквалбную строку, а не регулярное вырожение. Нужно чтобы слэши в пути (`srv/nfs/dhare`) не толковались как спецсимволы регулярки. 
* `2>/dev/null` -> перенаправляет ***stderr*** (поток ошибок, дескриптор 2) в *никуда*. Это на случай, если файла `etc/exports` еще не существует: тогда `grep` ругался бы в `stderr`, а так ошибка молча гасится. 
    * `then echo "${EXPORT_LINE}" >> /etc/exports` -> выполняется только тогда когда строки в файле нет. `>>` - дописать в конце файла ( в отличие от Ю, который перезаписал бы файл целиком и стер чужие экспорты)
> [!NOTE]
> **Итоговая логика:**
>
> *Проверяет, есть ли уже запись про `/srv/nfs/share`. Если ее нет -> дописывает, если она есть -> ничего не делает.*  

### Ⅲ `exports -ra`
> [!TIP]
> *Ты не видешь в этой команде списка экспортов, потому что она их не содержет, она читает иъ из файла.* Вот в чем связь: предыдущий блок записывал правило в `/etc/exports`, а `exports` - это инструмент, который берет модержимое `/etc/exports` и принимает его к работающему NFS-server.
> Файл `/etc/exports` - это *источник правды*, команда - исполнитель.
 
### Ⅳ Рвзбор логической связи с `firewalld`

```bash
if systemctl is-active --quiet firewalld; then
    log "Opening NFS ports in firewalld"
    firewall-cmd --permanent --add-service=nfs
    firewall-cmd --permanent --add-service=mountd
    firewall-cmd --permanent --add-service=rpc-bind
    firewall-cmd --reload
fi
```
* **firewalld** - служба-обертка над сетевым фильтром **Linux**, которая управляет тем, какие порты открыть. `firewall-cmd` - ее команда управления.
> [!TIP]
> ***Смысл всего блока:*** если на системе вклшючен `firewalld` - открой в нем порты нужные NFS; если `firewalld` нет или выключен - ничего нее трогай.

* `systemctl is active --quiet firewalld` - проверяет, ***запущен ли*** сервис *firewqalld*.
* `--quiet` = не печатает статус, возвращает только код возврата (0 -активен, иначе - нет).

> [!IMPORTANT]
>  **Выполняется только если `firewalld` активен:**
>     * `firewalld-cmd --permanent --add-service=`(`nfs`;`mount`;`rpc-bind`) - открывает 3 слубжбы. `--permanent` - записывает правило в конфиг, чтобы оно пережило перезагрузку и reload.

* Почему именно 3 службы? - потому что **NFSv3 требует трех компонентов** сразу:
    * `nfs` - сам протокол передачи данных;
    * `mountd` - [daemon](# "это фоновый процесс в Linux/Unix, который постоянно работает и обслуживает запросы, не привязанный к терминалу пользователя") монтирование, обрабатывает запрос клиента *"дай смантирую эту общую ситевую папку"*
